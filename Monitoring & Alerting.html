سند طراحی سیستم Monitoring و Alerting

طراحی یک سیستم ساده و قابل توسعه برای مانیتورینگ VM و سرویس‌های Docker، با تمرکز بر شاخص‌های ضروری و Alertهای قابل استفاده.

۱. خلاصه اجرایی

برای شروع، یک معماری سبک و ساده شامل Prometheus، Grafana، Node Exporter و cAdvisor پیشنهاد می‌شود.

Prometheus وظیفه جمع‌آوری و نگهداری Metricها را بر عهده دارد. Grafana برای ساخت Dashboard و مدیریت Alert استفاده می‌شود. Node Exporter اطلاعات خود VM را جمع‌آوری می‌کند و cAdvisor اطلاعات مصرف منابع کانتینرهای Docker را در اختیار Prometheus قرار می‌دهد.

تصمیم پیشنهادی برای مرحله اول برای شروع نیازی به Alertmanager، Loki، سیستم Trace یا ابزارهای پیچیده‌تر نیست. Alerting می‌تواند مستقیماً از طریق Grafana انجام شود.

۳. معماری پیشنهادی مرحله اول

Node Exporter متریک‌های VM
←
Prometheus جمع‌آوری Metrics
→
Grafana Dashboard و Alert
↑
cAdvisor متریک‌های Docker

تمام این اجزا می‌توانند به‌صورت Container روی همان VM اجرا شوند. برای یک VM و تعداد محدودی سرویس Docker، این معماری از نظر سادگی و قابلیت توسعه نقطه شروع مناسبی است.

نکته درباره خرابی کامل VM اگر Prometheus و Grafana روی همان VM باشند، در صورت خاموش شدن کامل VM خود سیستم Monitoring نیز از دسترس خارج می‌شود. مانیتورینگ بیرونی برای مرحله بعد در نظر گرفته می‌شود.

۴. اجزای سیستم

جزء نقش دلیل استفاده در مرحله اول
Prometheus جمع‌آوری، ذخیره و Query کردن Metricها هسته اصلی سیستم Monitoring
Grafana نمایش Dashboard و مدیریت Alert رابط کاربری مناسب و Alerting داخلی
Node Exporter جمع‌آوری اطلاعات سیستم‌عامل و VM مانیتورینگ CPU، RAM، Disk و Network
cAdvisor جمع‌آوری Metricهای کانتینرها مشاهده مصرف منابع Docker
آیا Prometheus و Grafana به‌تنهایی کافی هستند؟ خیر. Prometheus و Grafana خودشان Metric مربوط به VM و Docker تولید نمی‌کنند. برای جمع‌آوری این اطلاعات به Exporter نیاز است. با این حال، در مرحله اول می‌توان Alerting را داخل Grafana انجام داد و نیازی به Alertmanager نداشت.

۶. طراحی Alerting

Alert باید فقط زمانی ارسال شود که یک وضعیت غیرعادی برای مدت مشخصی ادامه داشته باشد. افزایش کوتاه‌مدت مصرف CPU یا RAM الزاماً Incident نیست و نباید باعث ارسال Alert فوری شود.

Alert شرط پیشنهادی مدت پایداری شدت
CPU بالا بیشتر از ۸۵ درصد ۱۰ دقیقه Warning
RAM کم کمتر از ۱۵ درصد RAM آزاد ۱۰ دقیقه Warning
Disk تقریباً پر بیشتر از ۸۰ درصد مصرف ۱۵ دقیقه Warning
Disk بحرانی بیشتر از ۹۰ درصد مصرف ۵ دقیقه Critical
Target Down عدم دریافت Metric ۳ دقیقه Critical
سرویس Unhealthy ناموفق شدن Healthcheck ۲ تا ۳ دقیقه Critical

روند ارسال Alert

۱. جمع‌آوری Metric

Exporterها وضعیت VM و کانتینرها را به Prometheus گزارش می‌کنند.

۲. ارزیابی شرط Alert

Grafana بررسی می‌کند که آیا مقدار Metric از آستانه تعریف‌شده عبور کرده است یا خیر.

۳. بررسی مدت زمان

اگر وضعیت برای مدت مشخصی ادامه داشته باشد، Alert فعال می‌شود.

۴. ارسال Notification

Alert از طریق Email، Slack، Telegram یا کانال ارتباطی انتخاب‌شده ارسال می‌شود.

۵. رفع مشکل و Recovery

پس از بازگشت وضعیت به حالت عادی، پیام Recovery ارسال می‌شود.

۷. وضعیت Unhealthy کانتینرها

Running بودن یک کانتینر الزاماً به معنی سالم بودن سرویس داخل آن نیست. ممکن است Process اصلی هنوز فعال باشد، اما برنامه نتواند به Database، Cache یا سرویس وابسته متصل شود.

برای سرویس‌های مهم باید Healthcheck تعریف شود. این Healthcheck معمولاً یک Endpoint مثل موارد زیر است:

  • Health: آیا برنامه زنده است؟
  • Ready: آیا برنامه آماده دریافت ترافیک است؟
نکته فنی cAdvisor برای مشاهده مصرف منابع کانتینرها مناسب است، اما برای تشخیص دقیق وضعیت Docker Health Status کافی نیست. برای Alert دقیق روی وضعیت healthy/unhealthy در مرحله بعد باید یک Health Exporter یا روش جمع‌آوری جداگانه اضافه شود.

در مرحله اول، برای سرویس‌های مهم می‌توان Healthcheck داخلی Docker را فعال کرد و در مرحله دوم وضعیت آن را به Prometheus منتقل کرد.

۸. روند برقراری سرویس Monitoring و Alerting

مرحله اول: مشخص کردن سرویس‌های مهم

ابتدا لیست کانتینرها تهیه می‌شود و سرویس‌ها به دو گروه تقسیم می‌شوند:

  • سرویس‌های حیاتی که باید برای آن‌ها Alert فعال باشد.
  • سرویس‌های کم‌اهمیت که فعلاً فقط Dashboard داشته باشند.

مرحله دوم: راه‌اندازی اجزای اصلی

Prometheus، Grafana، Node Exporter و cAdvisor روی VM راه‌اندازی می‌شوند و ارتباط آن‌ها با یکدیگر بررسی می‌شود.

مرحله سوم: اتصال Grafana به Prometheus

Prometheus به‌عنوان Data Source در Grafana ثبت می‌شود و دریافت Metricها مورد بررسی قرار می‌گیرد.

مرحله چهارم: ساخت Dashboardها

یک Dashboard برای VM و یک Dashboard برای کانتینرهای Docker ساخته یا از Dashboardهای آماده استفاده می‌شود.

مرحله پنجم: ساخت Alertهای ضروری

Alertهای CPU، RAM، Disk، Target Down و Healthcheck سرویس‌های مهم ایجاد می‌شوند.

مرحله ششم: اتصال Notification

یک کانال دریافت Alert مشخص می‌شود و Alertهای Warning و Critical در صورت نیاز به کانال‌های جداگانه ارسال می‌شوند.

مرحله هفتم: تست عملی

با ایجاد شرایط کنترل‌شده، عملکرد Alertها، ارسال Notification و پیام Recovery تست می‌شود.

۹. تست و معیار پذیرش

تست‌های ضروری

  • بررسی نمایش CPU و RAM VM در Grafana
  • بررسی نمایش فضای Disk در Grafana
  • بررسی نمایش کانتینرها در Dashboard
  • توقف یک کانتینر آزمایشی و بررسی ایجاد Alert
  • ایجاد موقت مصرف CPU بالا در محیط تست
  • بررسی ارسال Notification
  • رفع مشکل و بررسی ارسال Recovery
  • بررسی اینکه Alertهای تکراری بیش از حد ارسال نشوند

معیار پذیرش

  • Prometheus در دسترس است
  • Grafana به Prometheus متصل است
  • VM در Dashboard قابل مشاهده است
  • کانتینرها در Dashboard قابل مشاهده هستند
  • CPU VM مانیتور می‌شود
  • RAM VM مانیتور می‌شود
  • Disk VM مانیتور می‌شود
  • Target Down Alert فعال است
  • Notification تست شده است
  • Healthcheck سرویس‌های مهم مشخص شده است
